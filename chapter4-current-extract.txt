IMPLEMENTATION 
4.1 Introduction 
This chapter presents the implementation of the proposed product authentication 
system. The system was developed based on the design outlined in Chapter 3 and integrates 
a backend server, a PostgreSQL database, and a web -based user interface for both 
manufacturers and consumers. The purpose of this chapter is to explain how the proposed 
design was translated into a functional prototype and to describe how the implemented 
modules operate cohesively in practice.  
The completed prototype supports product regis tration, QR code generation, QR 
payload protection, product verification, scan logging, clone risk detection, product 
revocation, and tamper-evident ledger recording. The implementation focuses on delivering 
an end-to-end proof of concept within a controll ed environment. This chapter also outlines 
the system requirements, development setup, implementation details, and the overall 
workflow of the completed system. 
4.2 System Requirements 
4.2.1 Hardware Requirement 
The system was developed and tested using a laptop equ ipped with an AMD Ryzen 
5 processor with Radeon Graphics and 16 GB of RAM. This hardware configuration 
provided sufficient computational capability and memory to support local development, 
backend execution, database management, and browser-based testing.

4.4.2 Database Implementation 
The database was implemented according to the relational structure designed in 
Chapter 3 and refined to support the final prototype. It contains several interconnected tables 
that collectively support product registration, QR management, scan tracking, clone -risk 
evaluation, revocation management, and ledger recording.  
The product table stores the main product information, including product name, serial 
number, current status, and revocation reason. The qr_code table stores the unique QR 
identifier assigned to each product and its activation status. The scan_log table stores the 
history of verification scans, including QR reference, timestamp, IP address, device 
information, and app roximate location. The clone_risk table stores the most recent risk 
assessment for each QR code. The ledger_block table stores sequential tamper -evident 
ledger records for registration, verification, and revocation events.  
Relationships between these tabl es are maintained using foreign keys to preserve 
consistency between products, QR identifiers, scan history, and risk records. This relational 
structure provides both operational efficiency and traceability of critical system events.

4.4.5 QR Code Security Implementation 
QR code security was implemented by storing a cryptographically protected 
verification payload inside the QR code instead of storing raw product information. Each 
payload contains a non-sequential QR identifier, an issuance timestamp, and a cryptographic 
signature. This design reduces the risk of data exposure and makes QR tampering easier to 
detect.  
The backend generates the signature using HMAC -SHA256 together with a server-
side secret key stored in the environment configuration. During product registration, a signed 
payload is created and embedded into the verification URL. This URL is then encoded as a 
QR image and returned to the frontend.  
function signPayload(qrId, issuedAt) { 
  return crypto 
    .createHmac("sha256", getQrSecret()) 
    .update(`${qrId}.${issuedAt}`) 
    .digest("hex"); 
}

The clone detection mechanism was implemented as a heuristic process that 
evaluates recent scan behaviour within a configurable time window. The mechanism checks 
whether the same QR code is scanned from geographically distant locations within an 
unrealistic timeframe. It also considers repeated scans only when the scan locations are 
meaningfully different and exceed the configured distance threshold. Therefore, repeated 
scans from the same or nearby locations can still be treated as normal behaviour, reducing 
false positives during legitimate consumer use.

4.4.8 Ledger Block Integration 
A tamper -evident ledger was integrated into the system to provide an auditable 
record of critical produ ct-related events. The ledger stores product registration, product 
verification, and product revocation as sequential hash-linked blocks. Each block contains a 
unique identifier, the previous block’s hash, its own hash, the event type, a related reference 
identifier, and a timestamp.

4.5 System Workflow 
The overall workflow of the system begins when a manufacturer accesses the 
registration dashboard and enters the product details. These details are submitted to the 
backend server, where the system inserts the product record into the database and generates 
a unique non-sequential QR identifier. A signed verification payload is then  created using 
HMAC-SHA256 and embedded into a verification URL. This URL is converted into a QR 
code image and returned to the frontend for display and download. At the same time, a 
corresponding registration block is appended to the tamper-evident ledger.  



===== PAGE 29 =====
86 
Once the QR code is distributed with the product, a consumer can scan it using a 
mobile device. The verification page extracts the signed payload and sends it to the backend 
verification route. The backend validates the signature before performing any d atabase 
lookup. If the payload is valid, the backend retrieves the linked product and QR record, stores 
the scan log entry, evaluates clone-risk behaviour, checks the product status, and returns the 
final verification result.  
If the product is active and no suspicious behaviour is detected, the system returns 
an authentic result. If unusual scan behaviour is detected, the product is classified as 
suspicious and the frontend displays a recommendation warning. If the product has been 
revoked, the backend immediately returns a revoked result, and the frontend displays a red 
high-priority warning state. If the payload is invalid or cannot be matched to a registered 
record, the system returns an invalid result.  
Manufacturers can also revoke products through the  product list page. When a 
revocation request is made, the backend checks that the product is still active, updates the 
product status to revoked, disables the linked QR code, and records the revocation event in 
the ledger. Any later verification request f or that QR code will therefore return a revoked 
result.  
The workflow demonstrates how the frontend, backend, database, scan logging 
module, clone detection mechanism, and tamper-evident ledger operate together to support 
end-to-end product authentication in the prototype.
